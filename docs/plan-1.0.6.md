# План 1.0.6 — распознавание персонажа и внешности на устройстве

Дата: 2026-10-04. Все цифры проверены: размеры моделей — запросами к
Hugging Face API, состав APK — распаковкой собранного релиза 1.0.5.

Направление изменено после проверки: вместо большой генеративной модели
приложение получает маленький тегер и собирает текст шаблонами.
Причина — в разделе «Почему не LLM».

---

## Главная находка: 81% APK — это ML Kit

Распаковка `AMPS-1.0.5-release.apk`:

| состав | размер | доля |
|---|---|---|
| `lib/arm64-v8a/libmlkitcommonpipeline.so` | 10,5 МБ | |
| `lib/armeabi-v7a/libmlkitcommonpipeline.so` | 6,6 МБ | |
| `assets/mlkit_label_default_model/…tflite` | 2,9 МБ | |
| **итого ML Kit** | **19,99 МБ** | **81%** |
| `classes.dex` (весь код приложения) | 4,18 МБ | 17% |

ML Kit `image-labeling` выдаёт общие словари: «человек», «волосы»,
«одежда». Для аниме они бесполезны — с его помощью нельзя отличить
одного персонажа от другого.

**Замена ML Kit на аниме-тегер улучшает качество и почти не увеличивает
размер:**

| | APK |
|---|---|
| сейчас (1.0.5) | 24,6 МБ |
| без ML Kit | ~4,6 МБ |
| + тегер 30–45 МБ | **~35–50 МБ** |

## Почему не LLM

Проверено живыми запросами:

- **`Llama-3.2-Vision` на 3B не существует** — Meta выпустила только 11B
  и 90B. На 3B есть лишь текстовая модель без зрения. 11B в 4 битах —
  около 6–7 ГБ.
- **`Qwen2.5-VL-3B` не весит «1,5–2 ГБ»** — 4-битной версии нет,
  только fp16: 5 892 МБ + 1 276 МБ проектора = 7 168 МБ.
- **SmolVLM2-500M** (Apache-2.0) — 1 067 МБ в ONNX. Умеет описать
  картинку, но конкретный сериал по ней не назовёт.
- **MediaPipe LLM Inference** переведён Google в режим maintenance-only;
  мультимодальность на Android только с Gemma 3n — 3 486 МБ int4.
  Сам Google пишет: модель «too large to be bundled in an APK».

Даже самый малый вариант упирается в десятки мегабайт или в полтора
гигабайта. Задачу же решает не генерация текста, а извлечение тегов.

---

## Почему не база, выкачанная с чужих сайтов

- **animedia.com — не база аниме.** Компания ИИ-услуг: рендеринг,
  генерация сценариев, озвучка. Каталога аниме, жанров и персонажей на
  сайте нет. Проверено: отдаёт 200 со страницей об услугах.
- **shikimori.org отдаёт 403** с этой машины. У них есть GraphQL API, но
  их текстовые описания написаны редакторами сайта: это авторский
  контент, а не факты. Выкачивание базы и вшивание в чужое приложение —
  вопрос лицензии.
- **Jikan API** (бесплатный MyAnimeList) с этой машины не отвечает.

Для определения персонажа названия серий не нужны — нужны **теги**.
Названия серий уже приходят из AniList, который работает и подключён
с 1.0.5.

### MySQL в APK не запустится

Сервер MySQL на Android не работает: другая libc и другой набор
системных вызовов. Правильный выбор — **SQLite через Room** (Jetpack).
В приложении уже есть DataStore, переход небольшой.

### А сами векторы — копейки

| что | размер |
|---|---|
| 512 имён × 512 измерений (fp16) | 0,5 МБ |
| 5 000 персонажей в fp8 по 256 измерений | 1,2 МБ |

То есть вшивать нужно не базу аниме, а список тегов и канонических имён.

## Архитектура

| слой | что делает | размер |
|---|---|---|
| **тегер** `wd-swinv2-tagger-v3`, int8 | имена персонажей и признаки внешности | 30–45 МБ |
| **словарь тег → имя** | `aqua_hair` → «бирюзовые волосы», `hatsune_miku` → «Хацуне Мику» | 1–2 МБ |
| **шаблоны** | собирают из тегов связный текст | ~1 МБ |
| **AniList** (живой) | серия по найденному имени персонажа | уже работает |
| **IQDB** (живой) | источник, когда картинка уже в бо́ру-базе | работает с 1.0.5 |

Поток: картинка → тегер → теги → (а) имена персонажей → AniList →
страница серии, (б) признаки внешности → словарь → шаблоны → описание.

Теги тегера подставляются в ту же цепочку `searchCharacters` → `media`,
что собрана в 1.0.5. Тегер **расширяет** покрытие IQDB, а не заменяет
его: IQDB находит точное совпадение с источником, тегер работает с
любой иллюстрацией.

## Этапы

### Этап 1. Модель вне приложения

Никакого Android-кода. Тяжёлая зависимость ставится локально, тегер
прогоняется на контрольном наборе из `demo/` через ONNX Runtime.

**Критерий приёмки:** модель выдаёт осмысленные теги персонажей и
внешности минимум на половине картинок набора. Если нет — план
пересматривается, а не продолжается вслепую.

### Этап 2. Квантование

int8 через ONNX Runtime quantization. Квантованных версий SmilingWolf не
выпускает, поэтому делаем сами: `model.onnx` в fp32 — 446 МБ, int8
даёт около 112 МБ.

**Критерий приёмки:** доля верно распознанных тегов серии и персонажа
после квантования падает не более чем на 10 процентных пунктов.
Сравнение фиксируется числами, а не на глаз. Если падение больше —
остаёмся на fp32 и честно пишем про 446 МБ, либо пробуем меньший хребет.

### Этап 3. Удаление ML Kit

`ContentAnalyzer` переводится на теги тегера. Важное следствие: сигнал
«на картинке есть человек», который сейчас даёт ML Kit и используется
в `RankingEngine`, надо заменить — он выводится из наличия тегов
персонажа. Для аниме-картинки это надёжнее, чем общий словарь ML Kit.

**Критерий приёмки:** APK без ML Kit собирается и `classes.dex`
не ссылается на `com.google.mlkit`.

### Этап 4. Словарь и шаблоны

Выборка тегов, которые реально встречаются, с переводом на русский.
Шаблоны собирают описание: «На картинке — <персонаж>. <внешность>».
Каждый собранный текст должен быть помечен как составленный из тегов,
а не как распознанный факт.

### Этап 5. Проверка на живых данных

Контрольный набор прогоняется через весь конвейер, результаты пишутся
в `docs/`. Сравнивается с тем, что даёт IQDB на тех же картинках.

### Этап 6. Интерфейс

Экран результата показывает: имя персонажа (с пометкой «по тегам
источника», как в 1.0.5), признаки внешности, источник каждого вывода.
Ничего не додумывается: если тег не найден — так и пишется.

## Риски

1. **Скорость на телефоне неизвестна** — замеров на устройстве ещё нет.
2. **int8 может испортить теги** — проверяется этапом 2.
3. **ONNX Runtime добавляет ~25 МБ** (две архитектуры) и собственную
   модель памяти; на `minSdk 24` заявлена поддержка, но на старых
   устройствах может вести себя иначе.
4. **Приложение ни разу не запускалось на устройстве** — всё, что
   можно проверить без телефона, проверяется этапами 1–2 и 5.

## Где план остановиться, если не пойдёт

Если на этапе 1 тегер не выдаёт осмысленных тегов, 1.0.6 разумнее
направить на исправление текущего, а не накапливать модели, которые не
работают. Это дешевле, чем выпустить мегабайты кода, который не
определяет ничего.
