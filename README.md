# AMPS

**Поиск по картинке аниме и по музыке.** Android-приложение, которое по
иллюстрации, скриншоту или фото находит произведение и персонажа, собирает
вики-страницу с составом и источниками, а по названию трека — метаданные и
свободно лицензированный файл.

Рабочее название — **AMPS**. Пакет `dev.amps.app`, версия 1.0.5.

---

## Зачем это

Обычный поиск по картинке аниме отвечает на вопрос «что это за картинка».
AMPS отвечает на два вопроса сразу: **что это за произведение** (описание,
студия, состав, связи, рекомендации) и **кто изображён** (персонаж по тегам
источника). По названию песни приложение находит исполнителя, альбом, обложку
и — если у источника есть свободная лицензия — кладёт сам файл в музыкальную
библиотеку телефона.

**С 1.0.3 компьютер не нужен.** Раньше телефон отправлял снимок по домашней
Wi-Fi на ПК, а тот вызывал локальные MCP-серверы. Теперь IQDB, AniList,
Wikidata и вики фандомов вызываются напрямую с телефона, а логика взвешивания
вердикта живёт в самом приложении. Мост и папка `bridge/` удалены.

**С 1.0.5 ключей нет вообще.** Jamendo работает сразу, поиск по картинке идёт
через IQDB, который не требует ни ключа, ни регистрации. Вводить нечего.

### Ключи API

| Источник | Ключ | Что будет без него |
|---|---|---|
| IQDB | **не нужен** — ни ключа, ни регистрации | ничего: это единственный источник поиска по картинке |
| AniList | **не нужен** — публичный GraphQL | ничего: без него не найти серию по тегу персонажа |
| Jamendo | **уже вшит**, работает сразу | ничего для поиска CC-музыки |

Ключей у приложения нет вовсе, поэтому в APK не может лежать ничего
секретного. Это не защита, а отсутствие проблемы: APK — zip с открытым
содержимым, любая строка внутри читается обычным поиском по тексту, без
декомпиляции. Всё, что раньше требовало ключа SauceNAO, теперь делает IQDB.

### Как определяется персонаж

С этим пунктом важно быть честным, потому что обман здесь лёгкий.

- **IQDB ищет по картинке**, а не по кадру видео. Сервис опрашивает сразу
  Danbooru, Konachan, yande.re, Gelbooru, Sankaku Channel, e-shuushuu, Zerochan
  и Anime-Pictures, то есть это сборщик нескольких бо́ру-баз, а не одна база.
- **Имя персонажа лежит в тегах.** У Danbooru-подобных баз тег вида
  `belgium_(hetalia)` — это персонаж и серия в одной строке. Из него
  приложение берёт `belgium` и ищет персонажа в AniList.
- **Серия берётся из персонажа.** У найденного персонажа AniList отдаёт список
  появлений, отсортированный по популярности; самое популярное и становится
  ответом. Это новый способ получить серию: раньше её называл trace.moe по
  кадру видеозаписи.
- **Если персонажа по тегам нет, ищется серия по тегу серии** —
  `hetalia:_axis_powers` даёт `axis powers`, и AniList ищет по этому названию.
- **Совпадение в одной базе не считается подтверждением.** IQDB формально один
  источник, поэтому «определено» недостижимо, пока с высоким процентом не
  сойдутся хотя бы две независимые базы внутри одного ответа.
- **Кто именно изображён, и кто просто есть в серии — разные вещи.** Карточка
  «Персонаж» показывает только того, кого назвали теги; перечень состава серии
  подписан отдельно и никогда не выдаётся за «персонажа в кадре».

### Чего IQDB не умеет

Совпадение находится только если картинка уже лежит в индексе. Обычное фото
человека, скриншот из видеоигры или кадр, которого в базах нет, не найдутся.
Приложение в этом случае говорит прямо, что просмотрено и почему пусто, а не
изображает уверенную неудачу.

**Именно это происходит со скриншотами аниме.** IQDB индексирует бо́ру-базы —
fan art, косплей, иллюстрации. Кадров из серий там единицы. Замер на восьми
скриншотах: восемь ответов «No relevant matches», ни одного совпадения.

Для кадров из серий нужен другой принцип поиска, и он реализован отдельно —
см. [trace.moe](#trace-moe-1) ниже.

## trace.moe

Единственный источник, который отвечает на вопрос «это кадр из серии, из
какой». Он сравнивает не картинки целиком, а хеши кадров, поэтому находит
конкретный момент конкретной серии, а не «похожую картинку с похожим цветом
волос».

Сервис вернул серию на все восемь тестовых кадров, но сходство колебалось от
24 % до 72 %. Разброс объясним: скриншоты почти наверняка обрезаны или
отредактированы (субтитры, пережатие), а для поиска по хешу это снижает
сходство.

### Пропорции, а не разрешение

Позже выборка выросла до 21 картинки, включая семь из папки пользователя, и
разброс перестал быть разбросом — он разделился надвое:

| пропорции | сколько | сходство |
| --- | --- | --- |
| широкие, 1,6–2,1 | 4 | **96,2–100 %** |
| книжные и квадратные, меньше 1,2 | 14 | 24,0–70,5 % |

**Пересечения нет ни одного.** Широкие кадры дают среднее 98,1 %, остальные —
52,3 %. Разрешение тут ни при чём: книжная картинка 900×956 не хуже широкой
599×333 по качеству, хуже она по форме.

Порог 85 % стоит ровно в разрыве между группами, а не произвольно: ни один
книжный кадр до него не дотягивает, а все широкие — перекрывают.

Обрезка не восстанавливает совпадение, и это проверялось отдельно: у точного
кадра 640×360 сходство падает со 100 % до 93,4 при обрезке, дальше до 84,5 и
72,5 % по мере усечения. Поэтому приложение предупреждает о книжной картинке
заранее, а не молчит после неудачи.

### Почему проценту нельзя верить напрямую

trace.moe **отвечает всегда**, даже когда ответ бессмыслен. При 24 % сходства
он предлагает серию, к которой картинка отношения не имеет. Поэтому в коде
процент заменён на три состояния:

| Уверенность | Сходство | Что делается |
| --- | --- | --- |
| `TRUSTED` | от 85 % | серия называется прямо |
| `WEAK` | 50–85 % | называется с оговоркой «похоже, но не уверен» |
| `UNUSABLE` | ниже 50 % | наружу не идёт вовсе, даже если сервис что-то вернул |

**На тестовых кадрах до порога 85 % не дошёл никто.** Это правда, а не
недоработка: поднять порог ниже значит начать показывать шум.

Рядом с названием всегда показывается имя файла-источника — откуда взялась
серия. У trace.moe бывают устаревшие привязки к AniList: на одном из кадров он
вернул ID, который AniList отдаёт как «Metal Fight Beyblade», тогда как в файле
лежал «Beyblade: Metal Fusion».

## Имена персонажей и внешность — разные вещи

Тегер, встроенный в 1.0.6, обучен на Danbooru, то есть на фан-арте и косплее.
На скриншотах из серий он ошибается: максимум 0,53 и ни одного имени.

Но он **не молчал** — на кадрах выдавал чужих персонажей с уверенностью 0,73,
то есть говорил уверенно и неверно. Это хуже, чем отказ.

Поэтому с 1.0.7:

- **описание внешности** показывается всегда — цвет и длина волос, глаза,
  одежда там определяются верно;
- **имена персонажей** от тегера показываются только если серию подтвердил
  внешний источник (IQDB или trace.moe). Тогда гипотезу можно сверить с
  найденным и она перестаёт быть выдумкой;
- при промахе из описания собирается **поисковый запрос** и даются ссылки на
  DuckDuckGo, Яндекс и Google.

### Почему это ссылки, а не выдача поисковика

Проверено с рабочей машины: и DuckDuckGo, и Mojeek на автоматический запрос
отдают страницу с капчей — при коде 200 внутри находится
`anomaly-modal__puzzle` и `captcha-wrap` соответственно. То есть запрос
выглядит успешным, а внутри — антибот.

Собирать на этом выдачу значит вшить в приложение конструкцию, которая
рано или поздно сломается. Ссылка не ломается: её открывает обычный
браузер, где капчу при необходимости проходит человек.

### Почему не Brave Search

Brave Search API отвечает `422` без платного ключа, а MCP-серверы этой
сборки существуют на машине разработчика и в APK телефона не попадают в
принципе.

### Честное ограничение

Поиск по внешности **не находит персонажа надёжно**: «зелёные глаза и школьная
форма» — это половина всех героев аниме. Поэтому ссылки показываются как
подсказка для проверки, а не как ответ.

### Вырезанный персонаж на чужом фоне

С 1.0.8 это ограничение сделано видимым в приложении. Проверено на семи
картинках из папки пользователя, для которых известно содержимое —
`Itachi.webp`, `Natsu_X792.webp`, `Lightning_Emress_Armor.webp`:

| источник | результат |
| --- | --- |
| trace.moe | 0 из 3 — Inazuma Eleven вместо Наруто, Horimiya вместо Honkai |
| аниме-тегер | 0 из 3 — `suiseiseki` вместо Итачи и Нацу, `suigintou` вместо Цзинлю |
| тегер по обрезанному лицу | 0 из 3 — тот же неверный ответ с той же уверенностью |
| IQDB | 0 из 7 |

Причина у каждого своя. trace.moe сравнивает **кадры** целиком, а вырезанный
персонаж кадром не является. IQDB смотрит на всю картинку, и чужой фон
портит сходство. Тегер обучен на Danbooru, то есть на фан-арте, и вне своего
распределения не разбрасывается, а **схлопывается на один частый тег**: на
семи картинках он выдал всего три различных имени, все неверные, с
уверенностью 0,96–0,998. С 1.0.8 такие имена прячутся — повтор одного тега на
разных картинках выдаёт отказ модели.

Распознавания аниме-лица со свободной лицензией нет: InsightFace с ArcFace
раздаётся под лицензией «только некоммерческие исследования», у второй
кандидатки лицензия не указана. Детекция лица свободна
(`deepghs/anime_face_detection`, MIT) и работает — на обрезанном лице
уверенность 0,998, — но вектора она не выдаёт, а без него сравнивать нечем.
Кроп лица ничего не меняет: ответ тегера остаётся тем же неверным.

**Что работает:** полный широкий кадр из серии. trace.moe опознаёт его с
точностью 96,2–100 %. **Что не работает:** обрезанный, книжный или
квадратный персонаж. Приложение об этом предупреждает заранее.

## Как приложение решает, какое это произведение

Карточка не открывается сразу после первого ответа, каким бы ни было его
sходство. `RankingEngine` складывает находки в один балл и отвечает не «вот
аниме», а «вот аниме с такой-то уверенностью и по такой-то причине».

| Сигнал | Что даёт | Где живёт |
| --- | --- | --- |
| IQDB, лучшее совпадение | основной балл, сходство 0..100 % | внешний сервис |
| Независимые базы внутри IQDB | бонус за согласие Danbooru, Konachan, Gelbooru, Sankaku и других | тот же ответ IQDB |
| Бо́ру-теги → AniList | персонаж по тегу и серия по его появлениям | внешний сервис, без ключа |
| Аниме-тегер (1.0.6) | персонаж на любой иллюстрации + внешность | телефон, офлайн |

### Аниме-тегер

С 1.0.6 на устройстве работает не общий распознаватель, а аниме-тегер
`SmilingWolf/wd-swinv2-tagger-v3` (Apache-2.0), сжатый до int8 — 166,8 МБ.
Он заменил ML Kit, который занимал 20 МБ и знал только «человек», «волосы»
и «одежда».

Измерения на наборе из 36 картинок с заранее известным персонажем:

| | результат |
|---|---|
| правильный персонаж в первой пятёрке | **100 %** |
| правильный персонаж первым | 55,6 % (fp32), 52,8 % (int8) |
| уверенная находка | 0,73 |
| мусор на не-anime картинке | 0,50–0,53 |

Из этого выведены три решения:

- **Показывается пятёрка, а не один тег.** Правильный ответ в ней есть
  всегда, просто не всегда первый.
- **Порог 0,60.** Между мусором и находкой измеренный разрыв: ни одна
  настоящая находка не опускалась ниже 0,60, ни один мусор не поднимался
  выше 0,53.
- **Разрешение на вход не влияет.** Сжатие картинки до 230 px по ширине
  изменило итог на 0 из 21 проверок, поэтому модель тянет 448×448 так, как
  обучена, и картинку не надо заранее увеличивать.

На кадрах из видео тегер честно молчит — максимум 0,53 и ни одного имени.
Это корректный отказ «не иллюстрация», а не ошибка.

Ключевое отличие от прежней схемы: **подтверждение берётся не из числа
сервисов, а из числа независимых баз внутри одного ответа**. Отсюда три
состояния вместо одного:

- **Определено** — сходятся хотя бы две независимые базы с процентом не ниже
  70 %, итоговый балл выше 70 %, и IQDB пометил находку как точную;
- **Не уверен** — точное совпадение не найдено, базы спорят или согласилась
  только одна. Серия показана, но честно помечена, альтернативы перечислены
  рядом;
- **Не удалось определить** — совпадений нет или ответил только один источник,
  который не смог назвать серию.

Потолок `SINGLE_SOURCE_CAP` (55 %) действует и сейчас: совпадение в одной базе
не поднимает уверенность выше 55 % никаким процентом сходства. Это ровно то,
чего просили: много совпадений в процентах не выглядит как уверенность, а
неверное аниме не подаётся как факт.

### Что видно на картинке

Тегер работает офлайн, модель вшита в APK, картинка наружу не уходит. Он
знает и признаки внешности, и имена персонажей — в отличие от прежнего
ML Kit, который умел только «человек», «небо», «стол».

Признаки внешности — цвет и длина волос, одежда, украшения, поза, фон —
переводятся в описание по словарю из 220 тегов. Персонажи разрешаются
в имена через AniList: бо́ру-тег приводится к виду, который понимает поиск,
и уже по нему берётся каноническое имя.

Всё, что тегер выдаёт, подписывается как предположение по тегам, а не как
установленный факт — та же честность, что и в 1.0.5.

### Персонажи и места по вики

У аниме-записей в Wikidata нет утверждения «персонаж» — проверено, всегда ноль.
Поэтому имена берутся из категорий фандом-вики, а Wikidata служит только для
поиска самой вики (свойство P8080).

- Cowboy Bebop → Ed, Ein, Faye Valentine, Jet Black, Julia, Shin; места: Earth,
  Ganymede, Mars, The Bebop;
- Steins;Gate → 12 персонажей и 8 мест (Akihabara, Future Gadget Laboratory,
  Ayamein Women's Academy).

Если вики у серии нет, блок просто не показывается.

### Отпечаток картинки

В карточку попадает dHash-64 — перцептивный хеш изображения. Он не ищет
ничего и ни в какой внешний индекс не отправляется: его задача — отличить
«ту же самую картинку» от «похожей на неё», в том числе в истории поиска.

Наполнять его чужими картинками нельзя было и раньше, и это осталось верно:
на фандомах у картинок **нет лицензий** (сборщик получил 162 файла и отклонил
все 162), а в Internet Archive у предметов **нет AniList id**, и запись без
него в приложении бесполезна.

## Экраны

**Картинка.** Выбор изображения (системный выбор файла) или «поделиться» из
галереи. Картинка уменьшается до 1280 px и уходит на iqdb.org. Пока идёт поиск —
стадия прогресса; потом результат с круговым индиатором сходства.

**Вики.** Страница произведения:

- баннер, название, японское название, синонимы, чипы (год, формат, серии, статус);
- блок «Насколько уверены источники» — счёт, объяснение по пунктам, спорные
  предупреждения и альтернативные варианты;
- блок «Где нашлось совпадение» — база, сходство, точное ли совпадение и ссылка
  на найденную картинку; эпизода и таймкода там нет: IQDB по кадрам не ищет;
- описание, жанры, студия, оценка, популярность;
- «Персонаж» — тот, кого назвали по бо́ру-тегу, с подписью «по тегам источника»;
- «Персонажи этой серии» — отдельный блок с оговоркой, что это перечень серии,
  а не догадка о том, кто изображён на картинке;
- похожие изображения (все совпадения IQDB) и рекомендации AniList;
- список источников со ссылками — что откуда взято.


**Музыка.** Три вкладки: поиск, свободные треки, мои файлы. Поиск с debounce
420 мс. Метаданные сливаются по нормализованному ключу `исполнитель + название`:
при коллизии побеждает iTunes, строка MusicBrainz используется, только если
добавляет MBID. Вики-страница трека — обложка, лицензия, спецификация
(формат, битрейт, частота, длительность), источники, похожие треки и
настоящее воспроизведение через `MediaPlayer`.

**Настройки.** Ключей в приложении нет; Jamendo подключён сразу. Отсюда тема,
история, импорт скачанного в музыку телефона и честный список источников музыки.

**История.** Последние 60 находок — и картинки, и треки. Нажатие открывает
соответствующую вики-страницу.

## Лицензии: как это решается в коде

Правило простое: приложение не отдаёт файл, у которого нет читаемой свободной
лицензии. Это не надпись в интерфейсе, а структура типов.

- У `MusicSearchResult` **вообще нет аудиополя**. К строке из iTunes или
  MusicBrainz физически нельзя прикрепить кнопку скачивания. `previewUrl`
  из iTunes намеренно не разбирается.
- У `FreeTrack` есть `downloadable = license.isKnown && !audioUrl.isNullOrBlank()`.
  `isKnown` требует **и** название лицензии, **и** её URL. `fromUrl()` никогда
  не превращает неизвестную лицензию в известную.
- `MusicRepository.download()` перепроверяет лицензию **до открытия сокета**
  и бросает `IOException`, если она нечитаема.
- Флаги CC разбираются из пути URL (`/licenses/by-nc-sa/4.0` → by + nc + sa,
  версия 4.0), а не угадываются по подписи. Из них формируются обязанности:
  «требует указания автора», «только некоммерческое», «те же условия».
- `FreeTrackFilter.OPEN` перепроверяет лицензию на клиенте, потому что
  archive.org не умеет выразить «CC, но не NC» в своём языке запросов.
- Каждый скачанный или импортированный файл получает рядом
  `<файл>.kagami.json` с источником, идентификатором, автором, ссылкой,
  лицензией, атрибуцией и sha256 — обязанность CC-BY переживает переустановку.

Чего приложение **не** делает: не вытаскивает аудио из YouTube, Spotify,
Яндекс.Музыки и Deezer, не обходит DRM, не трогает закрытые по лицензии
записи. Свой файл импортируется системным выбором — это легально по
определению, и лицензия для него помечается «не указана (свой файл)» с
возможностью дописать её вручную.

## Обновления по воздуху

С 1.0.1 приложение само следит за релизами в этом репозитории — так же,
как это делает F-Droid.

1. При запуске спрашивает `GET /api/repos/Mugen00/AMPS_MK/releases/latest`.
   Репозиторий публичный, токен и никакие права не нужны.
2. Тег вроде `v1.0.1` разбирается в тройку (1, 0, 1) и сравнивается с
   установленной версией. Если новая больше — появляется сообщение
   «Доступно обновление».
3. APK скачивается с прогрессом, во временный файл, затем переименовывается.
4. Перед установкой проверяется, что в файле пакет `dev.amps.app`: чужой APK
   из релизов не поставится.
5. Установка идёт через системный установщик (`ACTION_INSTALL_PACKAGE`).
   Если система ещё не разрешила ставить из неизвестных источников,
   приложение объясняет это и открывает нужный экран настроек, а установка
   продолжается после возврата.

Все изменения каждой версии — в [CHANGELOG.md](CHANGELOG.md) и в примечаниях
к релизу.

## Сборка

Нужны JDK 17, Android SDK (platform 35, build-tools 35.0.0), Gradle 8.11+.

```bash
./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Релиз с минификацией R8 и сжатием ресурсов:

```bash
./gradlew assembleRelease
```

**Подпись.** Положите `keystore/amps.jks` и `keystore/keystore.properties`
со строкой `storePassword=…` — сборка подпишется релизным ключом.
Если файлов нет, используется отладочная подпись, и сборка всё равно
проходит. Сам ключ и его пароль в git не попадают (проверено `.gitignore`).

| | debug | release |
|---|---|---|
| размер | около 113 МБ | **101,0 МБ** |
| applicationId | `dev.amps.app.debug` | `dev.amps.app` |
| минификация | нет | R8 + shrinkResources |

**Почему release такой большой.** С 1.0.6 почти весь объём — это
аниме-тегер: `assets/models/anime_tagger_int8.onnx`, 166,8 МБ в
развёрнутом виде. Архиватор в APK ужимает его примерно вдвое, так что в
собранном файле он занимает около 68 МБ. Сама программа после R8 —
3,2 МБ, движок ONNX Runtime — 28,5 МБ на две архитектуры.

| состав release 1.0.6 | МБ |
|---|---|
| модель тегера (в развёрнутом виде) | 166,8 |
| модель после сжатия в APK | ~68 |
| `libonnxruntime.so` × 2 архитектуры | 28,5 |
| `classes.dex` — весь код приложения | 3,2 |
| **APK целиком** | **101,0** |

До 1.0.5 в APK попадали ещё и `x86` с `x86_64` — 23,6 МБ, которые нужны
исключительно эмуляторам; сборка ограничена `arm64-v8a` и `armeabi-v7a`,
то есть всеми реальными телефонами.

При первом запуске модель копируется из APK в файлы приложения и занимает
там 166,8 МБ.

### Почему модели нет в репозитории

Файл модели весит 166,8 МБ, а GitHub не принимает в репозиторий ничего
больше 100 МБ, а квота Git LFS у аккаунта исчерпана. Поэтому модель не в
git: задача `fetchAnimeTagger` в `app/build.gradle.kts` скачивает её при
сборке и **обязательно сверяет SHA256**; при несовпадении сборка падает и
файл удаляется. Битая модель в APK попасть не может.

```powershell
.\gradlew :app:fetchAnimeTagger   # скачать одну модель и проверить хеш
```

В установленном приложении модель по-прежнему лежит внутри APK — выбор
«вшить в APK» не менялся. Источник: `SmilingWolf/wd-swinv2-tagger-v3` на
Hugging Face, лицензия Apache-2.0.

## Что ещё стоит знать

- Приложение просит ровно два разрешения: `INTERNET` и `ACCESS_NETWORK_STATE`.
  Никакого доступа к галерее или хранилищу — файл выбирается через
  Storage Access Framework, доступ к нему выдаётся на одну операцию.
- Один жест «поделиться» из галереи: intent-фильтр принимает только
  изображения, и кадр сразу уходит в поиск.
- Ключей у приложения нет: IQDB и AniList работают без регистрации, Jamendo
  подключён открытым идентификатором. В APK нет ничего секретного.
- Изображение уходит только на iqdb.org и в память запроса; ни во временный
  файл на диске, ни в историю оно не попадает.
- История лежит в JSON-файле приложения (60 записей), библиотека музыки —
  в `filesDir/audio/library.json`.
- Поиск обновлений ходит на `api.github.com` без токена: публичный
  репозиторий, сколько угодно запросов не потратит ваши права.
- `REQUEST_INSTALL_PACKAGES` — «особое» разрешение, его нельзя выдать молча.
  Android спросит один раз, когда вы впервые нажмёте «Установить».
