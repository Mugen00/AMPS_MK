# Патчноуты

Все значимые изменения AMPS. Формат основан на
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — SemVer.

Релизы публикуются на GitHub: <https://github.com/Mugen00/AMPS_MK/releases>.
Приложение само проверяет их и предлагает обновление — руками ничего
скачивать не нужно.

## [1.1.2]

Реліз Спільноти: пости з фото й відео, лайки, репости, профіль, який можна
редагувати, — і те, про що просили ще з 1.1.0: ключ для аутентифікатора
копіюється кнопкою, а вхід із 2FA працює до кінця.

### Спільнота

Нова вкладка внизу. Зареєстровані користувачі публікують пости (текст до
1000 символів), прикріплюють фото (до 10 МБ) або відео (до 50 МБ), ставлять
лайки та роблять репости. Репост — внутрішній: чужий пост з'являється у
стрічці окремим рядком із позначкою «Репост від X», і лічильник видно всім.
На кожному пості — дата публікації; авто-видалення немає, пости лишаються
назавжди. Стрічка дозавантажується по кнопці «Показати ще».

Фото показуються прямо у стрічці; відео відкривається системним плеєром
за прямою адресою — у офлайн-збірці немає ExoPlayer, тому вбудованого
відтворення всередині стрічки чесно немає.

### Профіль

Ім'я, біо (до 280 символів) і аватар редагуються окремим екраном, який
відкривається зі стрічки. Профіль створюється на сервері ліниво — акаунти,
зареєстровані ще в 1.1.0, отримують його без жодних додаткових дій.

### Сесія переживає рестарт

Токени входу тепер зберігаються (DataStore), і після перезапуску
застосунок лишається в акаунті — у 1.1.0 доводилося входити знову.
Коли access-токен спливає (30 хвилин), він оновлюється refresh-токеном
сам, без зайвих екранів. Якщо refresh-токен теж скінчився (30 днів) —
застосунок чесно просить увійти знову.

### 2FA працює до кінця

- Ключ аутентифікатора копіюється кнопкою: і сам секрет (для ручного
  додавання в Google Authenticator), і otpauth-посилання (для Aegis та
  інших, хто вміє вставку).
- Вхід з увімкненою 2FA завершується повністю: спершу логін і пароль,
  потім код з аутентифікатора — у 1.1.0 сервер чесно відмовляв, бо
  ланцюжок не був добудований.

### Сповіщення

- «Завантаження» — трек завантажено, повідомлення з назвою і виконавцем.
- «Спільнота» — нові пости та лайки/репости ваших постів; перевірка йде
  раз на годину, поки застосунок відкритий, без push-сервісів.
- Дозвіл на сповіщення (Android 13+) запитується один раз при вході на
  екран Спільноти; відмова нічого не ламає.

### Чесно про межі

- Фонова перевірка Спільноти живе у процесі застосунку (WorkManager у
  офлайн-збірці відсутній): поки AMPS закритий, сповіщення не приходять.
- Медіа постів і аватри лежать у сховищі сервера; щоб вони переживали
  передеплої, на Railway потрібен Volume, змонтований у `/data`. Без
  тому файли зникають при кожному передеплої — база при цьому в безпеці.
- Відео в стрічці відкривається системним плеєром, а не грає всередині
  списку.
- Роздача медіа публічна: імена файлів — невгадувані UUID, але той, хто
  знає точну адресу, завантажить файл без акаунта.

## [1.1.1]

Реліз розпізнавання персонажа на фото та нового джерела музики. Завдання
були сформульовані як «розпізнавання персонажа по фото» і «більше
джерел для скачування» — обидва закриті в межах того, що джерела
дозволяють чесно.

### Розпізнавання персонажа на фото

Коли IQDB знаходить арт у базі Danbooru, застосунок читає повний список
тегів персонажів самого поста через відкритий JSON API (без ключа). Раніше
йшов лише обрізаний `alt` прев'ю зі сторінки IQDB, у групових артах від
нього залишалися один-два імені з кількох. Повні імена йдуть у ланцюжок
AniList першими — вони описують знайдений пост, а не догадку про нього.

### Нове джерело музики — Openverse

Офіційний агрегатор відкритих аудіо: Free Music Archive, freesound,
Wikimedia та інші, усе з ліцензією CC або в суспільному надбанні. Один
клієнт покриває одразу кілька бібліотек із списку дозволених у проєкті.
Дублікати Jamendo відсікаються клієнтом — прямий доступ до нього
вбудований із 1.0.3, копія з агрегатора була б дублем, а не джерелом.

### Чесно про межі

- Ім'я з'являється тільки для артів, які вже є в базі Danbooru: арта в
  базі немає — лишається ланцюжок гіпотез локального тегера, як раніше.
- Закриті пости Danbooru не віддають JSON анонімно — ланцюжок повертається
  до `alt`-тегів IQDB.
- Openverse без реєстрації обмежує частоту запитів; при вичерпанні ліміту
  джерело падає банером «Openverse не відповів», решта джерел працюють.
  Анонімна сторінка — до 20 записів; ключ реєстрації безкоштовний, окремого
  поля в налаштуваннях під нього поки немає.
- **FreePD не увійшов у реліз**: сайт закрився остаточно (2008–2025),
  перевірено перед випуском.
- Задній план (Railway) у цьому релізі не змінювався.

## [1.1.0]

Реліз серверних можливостей. Усе, що в 1.0.9 було перелічено як
«не вміє, бо немає сервера», отримало сервер: бекенд на Ktor,
розгорнутий на Railway із вашого GitHub-репозиторію.

### Бекенд (Railway, тека `backend/`)

| | |
|---|---|
| Реєстрація та вхід | JWT (access + refresh), паролі BCrypt |
| Підтвердження email | Resend API — код листом |
| Підтвердження номера | Twilio — код у SMS |
| Відновлення пароля | код на email, скидання без входу |
| Двохфакторний захист | RFC 6238 на сервері |
| Синхронізація | історія пошуку між пристроями |
| База | PostgreSQL (Railway), Exposed ORM, HikariCP |

REST API зібрано під `/auth/*`, перевірка стану — `GET /health`.
Розгортання — `backend/Dockerfile` (багатоетапна збірка, JRE Alpine
у рантаймі), конфігурація — `railway.toml` у корені репозиторію.

### Застосунок

- **Подвійний режим входу.** «Локальний» — як у 1.0.9, працює без
  інтернету; «Через сервер» — обліковий запис на бекенді з підтвердженням
  email, SMS-номера та скиданням пароля. Перемикач — на екрані входу.
- **`BackendApi`** — HTTP-клієнт на OkHttp + kotlinx.serialization, без
  Retrofit: збірка додатка не тягне нових залежностей і лишається офлайн.
- **`SyncManager`** — синхронізація історії пошуку з сервером:
  оптимістичне блокування номерами версій, конфлікт версій вирішує
  користувач, а не тиха втрата даних.
- **Адреса сервера в налаштуваннях** — `backendBaseUrl` (порожній —
  дефолтний URL Railway-проєкту).
- `versionCode` 13 → 14.

### Як розгорнути бекенд

1. `railway login` і `railway link` (проєкт із підключеним GitHub);
2. `railway add postgresql` — створить `DATABASE_URL`;
3. `railway variables set JWT_SECRET=… RESEND_API_KEY=… EMAIL_FROM=…` —
   повний список змінних у коментарях `railway.toml`;
4. `railway up` — або просто пуш у гілку, яку обслуговує Railway:
   збірка йде через Dockerfile.

### Чесні обмеження

- **Серверні функції працюють лише коли бекенд розгорнутий.** Без сервера
  застосунок поводиться як 1.0.9: локальні акаунти, гість, повний пошук.
  Локальні акаунти навмисно залишені основним шляхом — офлайн першим.
- **Повторне надсилання кодів.** Лист із кодом email приходить при
  реєстрації та при кожному вході з непідтвердженою поштою — окремої
  кнопки «надіслати ще раз» у 1.1.0 немає. Повторний SMS для телефону —
  у наступній версії.
- **Вхід облікового запису з увімкненою 2FA поки не завершено.** Сервер
  чесно відмовляє з поясненням: повний ланцюжок «логін → код 2FA» —
  задача наступної версії. Сам секрет і перевірка коду працюють.
- **OAuth для музики досі не доданий.** Причина не змінилася: Deezer по
  OAuth віддає лише метадані, Spotify вимагає платного Premium, і жоден
  не віддає повний трек — того, що дає чинна п'ятірка безкоштовних
  джерел, вони не додали б.
- **Бекенд перевірений компіляцією, не запуском.** Проти живої бази він
  підніметься на Railway вперше; серверна TOTP-реалізація ділить алгоритм
  із локальною, яку в 1.0.9 перевірено всіма шістьма векторами RFC 6238.
- **Застосунок, як і раніше, не запускало на живому пристрої** — змінені
  екрани перевірені компіляцією.

## [1.0.9]

Релиз аккаунтов и защиты. Появился вход, регистрация, гостевой режим и
двухфакторная аутентификация. Музыкальный поиск перестроен: отдельно
скачиваемое и отдельно «только метаданные».

### Аккаунты

| | |
|---|---|
| Регистрация | логин, пароль, проверка сложности при вводе |
| Вход и выход | сессия переживает перезапуск приложения |
| Гостевой режим | полный доступ, история **не** сохраняется |
| Смена пароля | с проверкой текущего |
| Хранение | приватное хранилище телефона, SQLite |

### Пароли

PBKDF2-HMAC-SHA256, 210 000 итераций, случайная соль 16 байт на
аккаунт, сравнение хешей за постоянное время.

**Про Argon2.** Argon2 лучше, но библиотеки в проекте нет, а сборка идёт
с `--offline` и не скачает зависимость. PBKDF2 входит в сам Android —
выбор продиктован ограничением сборки, а не убеждением, что он лучше.

### Двухфакторная защита

Реализация RFC 6238 целиком в приложении: Google Authenticator, Microsoft
Authenticator, Aegis и любой другой совместимый. Сервис для кодов не
нужен — телефон и аутентификатор считают их одинаково по общему секрету.

Проверено против всех шести эталонных векторов RFC 6238 (приложение B).

Принимается код ±1 окно (30 секунд) — часы телефона и аутентификатора
часто расходятся на секунды, и без запаса верный код отклонялся бы.

### Чего приложение не умеет

| пункт | почему |
|---|---|
| Подтверждение email | нет сервера, письмо отправить некуда |
| Подтверждение номера | нужна платная SMS-служба с ключом |
| Синхронизация между устройствами | нужен сервер и база |
| Восстановление пароля по почте | нет сервера, письмо отправить некуда |

Почта и номер сохраняются, но как справочные данные. Написать «подтверждён»
было бы враньём, поэтому в интерфейсе этого слова нет.

### Музыка: что скачивается, а что только описывается

Запрос «любая музыка, любой автор, любой жёнр» разобран на две части,
которые раньше смешивались в один список.

| источник | что даёт |
|---|---|
| Jamendo, ccMixter, Internet Archive | **файл можно скачать**, лицензия известна |
| MusicBrainz, iTunes | только метаданные и 30-секундные отрывки |

Раньше источники склеивались в порядке ответа, и первым мог оказаться тот,
который ничего не отдаёт. Теперь:

- точное совпадение названия выше, затем исполнитель, затем частичное;
- скачиваемое поднимается над «только метаданные» — вы просили получать
  музыку, а не читать о ней;
- лицензия видна до запуска поиска, а не после;
- если скачиваемого не нашлось, но метаданные есть, приложение говорит
  об этом прямо, а не показывает пустоту;
- упавший источник не роняет весь поиск: не ответил iTunes — остальные
  результаты всё равно показаны.

**Про OAuth.** Его не добавлено. Deezer отдаёт по OAuth только метаданные и
30-секундные отрывки, Spotify требует платного Premium, и ни один из них
не отдаёт полный трек. Ни один из них не дал бы того, чего не даёт нынешняя
пятёрка бесплатных источников, но добавил бы вход и ключи.

### Почему не Git

Аккаунты **не** хранятся в репозитории. История Git безвозвратна: удалённый
коммит не убирает блоб с хешем пароля из клонов, форков и кэшей GitHub.
Хеш пароля или секрет 2FA, однажды попавшие в коммит, остаются там навсегда,
и один утекший репозиторий раскрывает всех зарегистрированных сразу.

## [1.0.8]

Релиз честности. Приложение больше не делает вид, что умеет больше, чем
умеет, и учится читать форматы, которые раньше проглатывал.

### Форматы изображений

| было | стало |
|---|---|
| `TraceMoeClient` объявлял `image/jpeg` при отправке PNG или WebP | MIME определяется по сигнатуре байтов |
| HEIC с айфона не читался | через `ImageDecoder` на API 28+ |
| AVIF не читался | там же |
| превью всегда помечалось как JPEG | фактический формат |

Подпись заголовка врала сервису: тот получал `image/jpeg`, а байты были
другие. Теперь при нераспознанном формате картинка приводится к JPEG
самой, потому что этот путь у сервиса самый надёжный.

### Пропорции решают всё

На двадцати одной картинке, включая семь из папки пользователя, закон
оказался без исключений:

| пропорции | сколько | сходство trace.moe |
|---|---|---|
| широкие, 1,6–2,1 | 4 | **96,2–100 %** |
| книжные и квадратные | 14 | 24,0–70,5 % |

Пересечения нет ни одного. Теперь приложение прямо говорит, когда
картинка книжная, и предупреждает, что обрезка не поможет: проверено,
что обрезка точного кадра в портрет роняет сходство со 100 % до 72,5 %.

### Имена тегера прячутся, когда модель отказала

На вырезанных персонажах тегер выдаёт **один и тот же** набор имён на
разных картинках: на семи файлах всего три тега, причём все неверные.
Когда модель вне своего распределения, она не разбрасывается, а
схлопывается на частый тег. Такие имена больше не показываются.

### Чего приложение не умеет и не будет делать

Главная задача пользователя — «персонаж аниме, вырезанный на произвольный
фон». Проверено на семи таких картинках с известным содержимым
(Itachi, Natsu, Lightning Empress):

| источник | результат |
|---|---|
| trace.moe | 0 из 3 — назвал Inazuma Eleven вместо Наруто, Horimiya вместо Honkai |
| тегер | 0 из 3 — назвал `suiseiseki` вместо Итачи и Нацу, `suigintou` вместо Цзинлю |
| тегер по обрезанному лицу | 0 из 3 — тот же неверный ответ с той же уверенностью |
| IQDB | 0 из 7 |

Распознавания аниме-лица со свободной лицензией не существует:
InsightFace с ArcFace распространяется под лицензией «только
некоммерческие исследования», у второй кандидатки лицензия не указана.
Детекция лица есть и свободна (MIT), но без модели, выдающей векторы,
сравнивать нечем.

Вместо правдоподобного ответа приложение сообщает, что не уверено, и
даёт ссылки для ручного поиска. Это осознанный отказ от угадывания.

## [1.0.7]

Приложение перестало уверенно называть не того персонажа. Проверено на
восьми скриншотах аниме из пользовательского набора — раньше именно они
давали неверные ответы.

### Что выяснилось

Задача пользователя — «скриншот персонажа из аниме, ка�� он нарисован в
серии». Это не фан-арт. А модель, которую встроили в 1.0.6, обучена на
Danbooru, то есть на фан-арте и косплее. **Разные распределения данных.**

Замеры на восьми кадрах:

| источник | результат |
|---|---|
| IQDB | 0 из 8, отвечает «No relevant matches» |
| тегер (1.0.6) | 0 из 8; молчит либо называет не того с уверенностью выше порога |
| trace.moe | отвечает на все 8, но сходство 24–72 % — низкие значения шум |

Теггер при этом **не молчал**: на кадрах он выдавал чужих персонажей с
уверенностью 0,73, то есть говорил уверенно и неверно. Это хуже, чем
отказ.

### Что изменилось

- **trace.moe** (`TraceMoeClient`) — точный поиск кадра в базе серий.
  Единственный источник, который сравнивает хеши кадров, а не картинки
  целиком, поэтому единственный, кто отвечает на скриншотах аниме.
- **Честная уверенность.** `Confidence` (TRUSTED / WEAK / UNUSABLE)
  заменяет голый процент: ниже 50 % результат не показывается вовсе,
  потому что trace.moe отвечает всегда, даже когда ответ бессмыслен.
  Порог 85 %: на тестовых кадрах до него не дошёл никто, и это правда, а не
  недоработка. Рядом показывается имя файла-источника, чтобы было видно,
  откуда взялось название серии.
- **Имена персонажей — только при внешнем подтверждении.** Если серию не
  назвал ни IQDB, ни trace.moe, гипотезы тегера наружу не идут. Описание
  внешности остаётся всегда: там модель не ошибается.
- **Поисковая подсказка** (`AppearanceSearchClient`) — из описания
  собирается запрос и даются ссылки на DuckDuckGo, Яндекс и Google.

### Почему не Brave Search

Brave Search API отвечает `422` без платного ключа, а MCP-серверы этой
сборки существуют на машине разработчика и в APK телефона не попадают в
принципе. Поэтому используются источники без ключа.

### Почему нет разбора HTML поисковиков

Проверено: и DuckDuckGo, и Mojeek на автоматический запрос отдают страницу
с капчей — при коде 200 внутри находится `anomaly-modal__puzzle` и
`captcha-wrap`. Собирать на этом выдачу значит вшить в приложение то, что
рано или поздно сломается. Поэтому это ссылки, а не скрейпер.

### Осталось нерешённым

Надёжно опознать произвольный скриншот из серии по-прежнему нечем: IQDB не
индексирует кадры, тегер обучен на другом материале, а trace.moe отвечает
шумом ниже 50 %. Причина вполне возможна — скриншоты обрезаны или отредактированы
(субтитры, пережатие), а для поиска по хешу это снижает сходство.

## [1.0.6b] — 2026-10-04

Аниме-тегер вынесен в отдельный процесс. Версия после 1.0.6a: падение
продолжалось, и 1.0.6a его не вылечил.

### Что выяснилось

Телефон, на котором проверялось, имеет **6 ГБ оперативной памяти**. Модель с
рабочим набором занимает порядка 400–500 МБ, то есть нехватка памяти как
причина не подтверждается — версия 1.0.6a ошибалась.

Проверенный код (разрешение имён, сборка описания внешности, декодирование
картинки) на отсутствие небезопасных обращений чист.

Остаётся то, что нельзя закрыть Java-обработчиком: падение внутри ONNX
Runtime — это нативный SIGSEGV, который уносит процесс целиком.

### Что сделано

- `TagService` работает в отдельном процессе `:tagger`. Когда модель роняет
  процесс нативно, Android убьёт только его, а основной получит отключение
  связи и покажет «распознавание на устройстве недоступно». Поиск через IQDB,
  музыка и вики продолжат работать.
- Обмен через `Messenger`. Картинка передаётся временным файлом, а не в
  `Bundle`: JPEG весит мегабайты, а транзакция Binder ограничена примерно
  1 МБ, и большая картинка порвала бы связь сама по себе.
- Процесс поднимается один раз; если он умер или не поднялся, `tag()`
  возвращает `null` мгновенно и не мучает телефон повторными попытками.
- Исправлен ложный отказ: раньше второй вызов подряд, увидев пометку «привязка
  идёт», сразу получал `null`. Теперь вызовы стоят на замке и выходят по
  первому готовому соединению.
- `TaggerEngine.close()` освобождает нативную память при остановке сервиса —
  167 МБ, которых сборщик мусора не видит.

### Из 1.0.6a

- `catch (Throwable)` вместо `Exception`: нехватка памяти — это `Error`.
- `android:largeHeap="true"`.
- Проверка свободной памяти до загрузки модели.
- Декодирование уменьшает картинку до 1280 px.

### Оговорка

**Ни одна из правок не проверена на устройстве** — телефона нет. Отдельный
процесс устраняет класс падений, а не конкретную причину: если упало не
только распознавание, а что-то ещё, 1.0.6b этого не покажет. Тогда нужен
`adb logcat` — без него мы гадаем.

## [1.0.6a] — 2026-10-04

Исправление падения на телефоне, найденного на живом устройстве.

### Симптом

Приложение падало через несколько секунд после разбора кадра, без
сообщения об ошибке. На тестовом наборе из 36 картинок всё работало —
падение проявлялось только на телефоне.

### Причина

Модель весит 167 МБ, и на устройстве с 2 ГБ ОЗУ памяти ей не хватало.
Три ошибки усугубили это:

- обработчик ловил `Exception`, а нехватка памяти приходит как
  `OutOfMemoryError` — это `Error`, мимо обработчика;
- свободная память не проверялась до загрузки модели: загрузка, которой
  памяти не хватило, роняет процесс нативно внутри ONNX Runtime, и поймать
  это нечем;
- в манифесте не было `largeHeap`, поэтому потолок кучи был стандартным.

### Исправлено

- `catch (Throwable)` вместо `Exception`, с отдельным пропуском отмены
  корутины наружу.
- Проверка свободной памяти **до** загрузки модели. Если её не хватает,
  модель не грузится вообще, приложение пишет «распознавание на устройстве
  недоступно», а поиск через IQDB работает как раньше.
- `android:largeHeap="true"` в манифесте.
- Декодирование картинки теперь уменьшает её до 1280 px по длинной стороне.
  Раньше картинка до 8192 px отвергалась, но 8192×8192 в ARGB_8888 — это
  268 МБ, то есть отказ срабатывал уже после потери памяти.
- Утечка второй сессии модели при гонке двух потоков закрыта.

### Оговорка

**Исправление не проверено на устройстве** — телефона нет. Версия основана
на разборе симптома: «упало через несколько секунд после анализа, без
сообщения» — типичный признак нехватки памяти, но это остаётся версией.
Если падение повторится, модель придётся заменить на меньшую.

## [1.0.6] — 2026-10-04

Приложение научилось называть персонажа **на самой картинке**, даже если этой
картинки нет ни в одной бо́ру-базе. Взамен общий распознаватель ML Kit.

### Заменено

- **ML Kit `image-labeling` → аниме-тегер `wd-swinv2-tagger-v3`** (Apache-2.0),
  сжатый до int8, 166,8 МБ.
- ML Kit занимал 20 МБ — 81 % APK — и знал только «человек», «волосы»,
  «одежда». Имён персонажей он не знал в принципе.
- Тегер даёт и внешность, и имена. Имена разрешаются в канонические через
  AniList по правилу: всё от первой скобки отбрасывается, `_` — это пробел
  (`rem_(re:zero)` → `rem`, `artoria_pendragon_(alter_swimsuit_rider)_(fate)`
  → `artoria pendragon`).
- Описание внешности собирается из 220 переведённых тегов, сгруппированных
  по смыслу: кто, волосы, глаза, одежда, украшения, поза, фон.

### Почему показывается пятёрка, а не одно имя

Измерения на наборе из 36 картинок с заранее известным персонажем
(Konachan, эталоны — теги danbooru):

| | результат |
|---|---|
| правильный персонаж в первой пятёрке | **100 %** |
| правильный персонаж первым | 55,6 % (fp32), 52,8 % (int8) |
| расхождение выходов int8 с fp32 | 0,029 |

Правильный ответ в пятёрке есть всегда, просто не всегда на первом месте.
Поэтому наружу отдаётся пятёрка с процентами, а не один тег.

### Порог 0,60 — измеренный разрыв

| | вероятность |
|---|---|
| уверенная находка | 0,73 |
| мусор на не-anime картинке | 0,50–0,53 |

Ни одна настоящая находка не опускалась ниже 0,60, ни один мусор не
поднимался выше 0,53. Между ними пусто, поэтому порог 0,60 отсекает шум,
не задевая находки.

### Разрешение на вход не влияет

Один и тот же набор прогнан в исходном разрешении и после сжатия до 230 px
по ширине — ровно так лежат картинки в приложении. Итог совпал **13 из 13**
и 21 из 21: разрешение ни при чём, модель тянет 448×448 как обучена.

### На кадрах из видео тегер молчит

Максимум 0,53 и ни одного имени на 13 кадрах из видео. Это корректный
отказ «не иллюстрация», а не ошибка: раньше такие картинки молча
показывали чужих персонажей.

### Честность интерфейса

Всё, что даёт тегер, подписано как предположение по тегам — тем же языком,
что в 1.0.5. Догадки наружу не выдаются за факты.

### Оговорки

- Цифры получены на наборе из популярных персонажей; на редких и на
  кадрах из видео модель молчит.
- Модель развёрнута на 166,8 МБ, но архиватор в APK ужимает её примерно
  вдвое, поэтому APK вырос с 24,6 МБ до **101,0 МБ** (из них 68 МБ — модель,
  28,5 МБ — ONNX Runtime на две архитектуры, 3,2 МБ — весь код приложения).
  При первом запуске модель распаковывается в файлы приложения и занимает
  там 166,8 МБ.
- **Модели нет в репозитории:** файл больше 100 МБ, а GitHub такие файлы в
  git отклоняет, и квота Git LFS у аккаунта исчерпана. Задача
  `fetchAnimeTagger` скачивает модель при сборке и сверяет SHA256 — при
  несовпадении сборка падает. В APK модель лежит как обычный ассет.
- Приложение **по-прежнему ни разу не запускалось на физическом устройстве**.
  Модель проверена прогонами на JVM, но запуск на Android, копирование
  166,8 МБ при первом старте и потребление памяти проверяются только
  установкой.

## [1.0.5] — 2026-10-04

Приложение ищет не по кадрам видео, а по самой картинке: иллюстрации,
скриншотам и фото. trace.moe из проекта удалён, SauceNAO заменён на IQDB.

### Изменено

- **Поиск идёт через IQDB, ключ не нужен.** `iqdb.org` спрашивает сразу
  Danbooru, Konachan, yande.re, Gelbooru, Sankaku Channel, e-shuushuu, Zerochan
  и Anime-Pictures и отвечает списком совпадений с процентами и бо́ру-тегами.
  Ни регистрации, ни ключа, ни квоты, которую пришлось бы вшивать в APK.
- **Серия теперь определяется по бо́ру-тегам, а не по кадру видео.** Раньше
  произведение называл trace.moe, который умел только кадры записей. Теперь
  цепочка такая: тег персонажа (`belgium_(hetalia)` → `belgium`) ищется в
  AniList, берётся самый популярный персонаж по `favourites`, а серия — из его
  появлений. Если персонажа по тегам нет, ищется серия по тегу серии
  (`hetalia:_axis_powers` → `axis powers`).
- **Один источник не может дать «определено».** IQDB формально один сервис, и
  он ошибается: 99 % в одной базе означает «очень похоже на то, что там
  лежит», а не «это то самое произведение». Прежний потолок
  `SINGLE_SOURCE_CAP` сохранён. Подтверждением считается согласие нескольких
  **независимых бо́ру-баз внутри одного ответа** IQDB с процентом не ниже 70 %.
  Бонус дают подтверждённый AniList персонаж и серия, названная по тегу.
- **Если IQDB не нашёл точного совпадения, решение не может быть «определено»**
  — максимум «не уверен», и в предупреждениях пишется почему: все совпадения
  помечены как «похожие», а не «Best match».
- **Эпизод, таймкод и ссылка на сцену убраны из карточки.** У IQDB их нет, а
  выдумывать их значило бы показывать правдоподобную, но несуществующую
  секунду. Вместо них — какая база ответила, с каким сходством, точное ли это
  совпадение и ссылка на найденную картинку.

### Исправлено

- **Пустые файлы при скачивании больше не попадают в библиотеку.** Jamendo и
  другие CDN периодически отвечают `200 OK` с пустым телом или со страницей
  ошибки; раньше такой ответ считался скачанным треком, и пользователю
  показывалось «Файл сохранён». Теперь нулевой файл, файл без аудиосигнатуры
  (ID3, MPEG, RIFF/WAVE) и файл, заметно меньше ожидаемого, отбраковываются до
  попадания в библиотеку, а временный файл удаляется.
- **Поиск серии в AniList снова работает.** `Page.media` и `Page.characters`
  AniList отдаёт простым массивом, а не связью с `nodes`. Старый разбор на
  такой схеме молча возвращал пустой список — то есть «персонаж не найден»
  вместо «схема изменилась». Клиент теперь принимает оба вида ответа.

### Про персонажа и состав серии

Раньше карточка называлась «Персонаж в кадре» и показывала первого кандидата
из AniList, даже если совпадение по тегам не нашлось вовсе. Это прямой обман:
перечень персонажей серии ничего не говорит о том, кто изображён.

Теперь:

- сверху — только тот, кого источник назвал по тегу и кого подтвердил AniList,
  с подписью **«по тегам источника»**;
- ниже — весь состав серии с явной оговоркой: «кто именно в кадре,
  определяет только совпадение по тегам»;
- если IQDB ничего не нашёл, так и написано: обычное фото или скриншот из
  видеоигры в бо́ру-базах не лежат, и выдумывать нечего.

### Убрано

- **Ключ SauceNAO из настроек.** Вводить больше нечего: поиск по картинке
  ключей не требует. Старый ключ остаётся в файле настроек мёртвой записью —
  ничего не ломает и удалять его при обновлении рискованнее, чем оставить.
- **Упоминания trace.moe и SauceNAO в интерфейсе и README.**

### Чего по-прежнему нет

IQDB ищет по тому, что уже лежит в индексе. Обычное фото человека, скриншот
из видеоигры или кадр, которого в базах нет, не найдутся — и приложение об
этом скажет прямо, вместо того чтобы изображать уверенную неудачу.

## [1.0.4] — 2026-10-04

Релиз 1.0.3a оказался недостижим: обновление о нём не приходило. Причина —
в разборе номера версии.

### Исправлено

- **Приложение больше не молчит о новых релизах.** `parseVersion` брал patch
  через `toIntOrNull()` и на любом непонятном значении молча подставлял `0`.
  Тег `v1.0.3a` разбирался как `1.0.0`, поэтому у пользователя с `1.0.3`
  выполнялось `1.0.0 <= 1.0.3` — «вы на последней версии», уведомления нет,
  и приложение даже не подозревало, что ошиблось. Теперь:
  - буквенный суффикс патча понимается и участвует в сравнении
    (`1.0.3` < `1.0.3a` < `1.0.3b` < `1.0.4`);
  - нераспознанный номер возвращает `null` и показывается пользователю как
    ошибка, а не превращается в `0.0.0`.

### Почему номер 1.0.4, а не 1.0.3b

Опубликованный 1.0.3a собран со сломанным разбором версий, поэтому он не может
достичь пользователя: его собственный парсер прочитает и `v1.0.3b`, и любой
буквенный тег как `1.0.0` и решит, что обновляться не нужно. Исправление
обязано прийти под обычным числовым тегом, который читается верно и старым
парсером. Поэтому 1.0.3a пропущен, а 1.0.4 несёт и правки 1.0.3a, и починку
разбора версий.

## [1.0.3a] — 2026-10-04

Патч к 1.0.3: две правки, найденные при проверке на живых ключах.

### Исправлено

- **Ошибка SauceNAO больше не выглядит как «совпадений нет».** SauceNAO
  отдаёт ошибку **внутри JSON с кодом 200**: код лежит в поле `header.status`,
  а пояснение — в `header.message`. Приложение читало `status` с корня
  ответа, где его нет, поэтому любой отказ — «анонимный аккаунт не допускает

  «SauceNAO ничего не нашёл» и искал проблему в кадре вместо того, чтобы
  посмотреть на ключ. Теперь причина отказа появляется в вердикте дословно.
- **Причина сбоя второго источника доходит до экрана.** Исключение
  SauceNAO поглощалось и никуда не попадало. Теперь оно передаётся в
  `RankingEngine` и показывается в списке предупреждений. Отказ второго
  источника по-прежнему **не роняет поиск**: trace.moe отвечает самостоятельно.

### Добавлено

- **Jamendo работает сразу, без настроек.** `client_id` зашит как значение по
  умолчанию. В отличие от ключа SauceNAO, это не секрет: Jamendo выдаёт его
  клиентским приложениям именно для того, чтобы они жили внутри них, и
  ограничивает им частоту запросов, а не квоту аккаунта. Поле ввода убрано из
  настроек — вводить нечего.

## [1.0.3] — 2026-10-04

Запрос: «убираем локальный мост вообще полностью, делаем приложение
работоспособным с интернет соединением».

Главное изменение — **приложение больше не нуждается в вашем компьютере**. До
1.0.2 телефон отправлял снимок на ПК по домашней Wi-Fi, а тот вызывал локальные
MCP-серверы. Теперь все источники вызываются напрямую с телефона, а папка
`bridge/` удалена из проекта целиком.

### Добавлено

- **Импорт в музыкальную библиотеку телефона.** Скачанный трек кладётся в
  `Музыка/AMPS` с тегами и обложкой и открывается любым системным плеером.
  Раньше файл оставался внутри приложения и был не виден плеерам. Теги
  записываются прямо в байты файла (ID3v2.4): публичного API для записи тегов в
  Android нет, а запись через `ContentResolver` затирается при каждом
  пересканировании.
- **Jamendo как источник музыки.** Первый источник, который отдаёт **полный
  трек** вместе с открытой лицензией. Ключ нужен только для поиска — сам файл
  отдаётся и без него по уже найденной ссылке.
- **Ключ SauceNAO в настройках приложения.** Второй источник подтверждения
  вердикта. Ключ хранится только на устройстве и не вшит в APK: вшитый ключ
  извлекается из приложения, а квота — того, кто его выдал.
- **Фанагентская вики читается напрямую.** MediaWiki `api.php` вместо
  обёртки. Состав персонажей берётся из категорий вики, а связь с Wikidata идёт
  через P8080 в ту же сторону — сиделинков на fandom нет.

### Изменено

- **Взвешивание вердикта перенесено в приложение.** Логика, которая раньше жила
  в мосте, теперь считается на телефоне — коэффициенты, пороги и правила те же.
- **Поиск больше не зависит от домашней сети.** trace.moe, SauceNAO, AniList,
  Wikidata и вики вызываются напрямую по HTTPS.
- **Скучная сводка — теперь с запасным путём.** `prop=extracts` есть не на
  каждой вики, поэтому при его отсутствии текст берётся из `action=parse`.

### Безопасность

- **Запрещён открытый HTTP.** Раньше ради моста на `http://192.168.x.x:8787`
  приложение разрешало незашифрованный трафик целиком — Android не умеет
  разрешить HTTP для одного адреса. Мост убран, и незашифрованный трафик теперь
  запрещён полностью.

### Убрано

- **Локальный мост и вся папка `bridge/`.** Удалено 23 файла Node.js.
- **Настройки адреса моста, UDP-обнаружение, карточка состояния моста.**

### Известные ограничения

- **Без ключа SauceNAO вердикт опирается на один источник** и честно
  помечается как неуверенный. Приложение сообщает об этом до поиска.
- **Google Vision и Google Lens в приложение не вошли.** Обратный поиск по
  фото через Vision требует OAuth и биллинга, а ключ в APK извлекается;
  `lens.google.com/uploadbyurl` отдаёт 404. Разбор содержимого на устройстве
  делает ML Kit — без ключа и без оплаты.
- **Epidemic Sound, Music Assistant и Free Your Music недоступны с телефона.**
  Первый требует бэкенд и запрещает выкладку на бесплатном тарифе, второй —
  всегда включённый сервер, третий — десктопное приложение. Это посредники, а
  не источники данных: то, что стоит за ними, доступно напрямую.

## [1.0.2] — 2026-10-03

Запрос: «определять, что находится в изображении — место, персонаж, предмет»,
«проверять сайты фандомов аниме, вики, делать перебор вариантов»,
«фильтровать, чтобы не было много совпадений в процентах и неверного аниме»
и «искать не только по кадрам из баз, а по разным источникам».

Главное изменение — приложение перестало доверять первому попавшемуся ответу.
Раньше карточка появлялась сразу после trace.moe, каким бы ни было его
сходство. Теперь решение принимают четыре независимых источника сразу, а
результат показывается вместе с уверенностью и объяснением.

### Добавлено

- **Разбор содержимого кадра на самом телефоне.** ML Kit (офлайн-модель, без
  Play Services) определяет людей, место и предметы прямо на снимке. Кадр никуда
  не отправляется — анализ идёт локально.
- **Взвешенный вердикт «Насколько уверены источники».** Вишенка приходит в
  приложение уже взвешенной: trace.moe, SauceNAO, индекс кадров и метки
  содержимого складываются в один балл с понятными причинами.
- **Три честных состояния вместо одного.** «Определено», «Не уверен: источники
  расходятся» и «Не удалось определить уверенно». Во втором случае показываются
  альтернативы — пользователь выбирает сам, вместо того чтобы получить неверное
  аниме как факт.
- **Персонажи и места по фандом-вики.** Приложение находит вики серии по
  Wikidata и читает её категории: настоящие имена и места вместо QID.
  У Cowboy Bebop это Ed, Ein, Faye Valentine, Jet Black, Julia и Shin;
  места — Earth, Ganymede, Mars. У Steins;Gate — 12 персонажей и 8 мест
  (Akihabara, Future Gadget Laboratory, Ayamein Women's Academy).
- **Каталог аниме на мосте.** 2000 серий с AniList, 12-часовой кэш, точечный
  запрос по id для серий вне кэша.
- **Индекс кадров с перцептивным хешем.** dHash-64, совпадает между мостом и
  приложением побайтово — проверено на реальном кадре, расхождение 0 бит.
- **Приложение само наполняет индекс.** Каждый кадр, который trace.moe
  подтвердил, отправляется в индекс моста. Это единственный легальный источник
  кадров: у пользователя есть файл, и он сам видел, что это за серия.

### Что работает честно, а что нет

Важно понимать до обновления.

- **Имена персонажей и мест берутся из вики, а не из модели.** ML Kit понимает
  «человек», «небо», «стол», «книга» — но не понимает, что это Кудо Ичиро.
  Названия приходят из AniList и фандом-вики. Если вики у серии нет, блок
  «Фандом-вики» просто не показывается.
- **Wikidata для персонажей бесполезен.** У реальных аниме-записей в нём нет
  утверждения «персонаж» — проверено на нескольких тайтлах, всегда ноль. Поэтому
  имена берутся из категорий вики, а Wikidata используется только для поиска
  самой вики.
- **Индекс кадров нельзя наполнить чужими картинками.** Фандом не проставляет
  лицензии (162 картинки, все отклонены), а в Internet Archive у предметов нет
  AniList id. Сборщик честно печатает разбивку по причинам отказа. Индекс
  растёт от кадров, которые подтвердил сам пользователь.
- **Прогрессивный JPEG не читается мостом.** Только baseline — так камеры
  телефонов отдают снимки экрана. С прогрессивного файла будет внятная ошибка,
  а не молчаливо неверный хеш.
- **Ответ trace.moe остаётся совместимым с 1.0.1.** Формат `/api/frame/identify`
  не изменён — старые телефоны и новый мост работают вместе.

### Исправлено

- Мост больше не путает HTTP-метод и префикс маршрута: из-за ошибки приоритета
  операторов любой незнакомый путь попадал в обработчик каталога и отвечал
  «400 bad anilist id» вместо 404.
- Тела POST-запросов разбираются как JSON: `ctx.body` — это `Buffer`, и проверка
  «это объект?» проходила для любых байтов, из-за чего ранжирование получало
  пустые сигналы и всегда отвечало «rejected».
- Ускорена загрузка каталога: задержка между страницами, отступ при 429 и
  фоновое обновление по устареванию — AniList больше не блокирует поиск.

## [1.0.1] — 2026-10-02

### Добавлено

- **Поиск моста без ручного ввода.** Мост отвечает на UDP-широковещание
  `AMPS_DISCOVER_V1` на порту 8788 и в ответе отдаёт свой HTTP-адрес,
  версию, состояние ключей и готовность MCP-узлов. Приложение рассылает
  запрос в подсеть, проверяет ответ через `GET /api/health` и кэширует
  найденный адрес на 10 минут.
- **Работа без моста.** Если мост не найден, кадр уходит напрямую в публичный
  HTTPS-API trace.moe (`POST https://api.trace.moe/search`) — ключ не нужен,
  работает анонимная квота по IP. Серия, эпизод, таймкод и сходство
  определяются, недостающие данные приложение добирает из AniList. Единственное,
  что теряется, — теги SauceNAO, то есть автоматическое определение персонажа.
- **Обновление по воздуху.** Приложение спрашивает
  `GET /api/repos/Mugen00/AMPS_MK/releases/latest`, сравнивает тег с установленной
  версией и, если новая есть, пишет «Доступно обновление 1.0.1». APK
  скачивается с прогрессом, проверяется по размеру и имени пакета, затем
  устанавливается системным установщиком — так же, как в Android.
- **Экран обновлений** с текущей и последней версией, примечаниями к релизу,
  прогрессом загрузки и кнопкой установки. Если система ещё не разрешила
  ставить неизвестные приложения, приложение объясняет это и открывает нужный
  экран настроек, а установка продолжается после возврата.
- **Патчноуты в репозитории** — этот файл плюс примечания к каждому релизу.

### Переименование

Репозиторий переименован в [Mugen00/AMPS_MK](https://github.com/Mugen00/AMPS_MK).
Старое имя `Mugen00/ASMP` GitHub перенаправляет само, но проверка обновлений
обращается к новому адресу, чтобы не ходить по редиректу. Релиз 1.0.0 и его
вложения никуда не делись.

### Изменено

- Настройка адреса моста больше не обязательна: поле осталось как ручное
  переопределение для нестандартных сетей, но по умолчанию используется
  автообнаружение.
- Мост печатает при старте строку `discovery: UDP 0.0.0.0:8788`, а в
  `/api/health` появился блок `discovery` с портом и признаком активности.
- `versionCode` 1 → 2.

### Исправлено

- Ответчик автопоиска отдавал адрес **телефона**, а не свой: `rinfo.address` в
  UDP — это отправитель. Теперь адрес отправителя лишь выбирает, какую из
  локальных сетевых карт объявлять (по совпадению подсети), а в ответе
  добавляется список `ips`.
- Эндпоинт trace.moe: `/v2/trace` больше не существует — проверено живым
  запросом, отдаёт `Cannot POST /v2/trace`. Рабочий — `POST /search`.
- Три обращения к скрытому API, которых нет в публичном SDK (проверено по
  `android.jar` для API 35): `Settings.ACTION_MANAGE_APP_INSTALL_UNKNOWN_SOURCES`,
  `LinkProperties.getGateway()` и `android.net.LinkRoute`. Заменены на публичные
  аналоги; чтение шлюза убрано — при broadcast-поиске оно не нужно.
- Релизная сборка больше не тянет `lint-gradle` из сети: проверка lint
  отключена в `build.gradle.kts`, иначе `assembleRelease` падал офлайн.
- Временные файлы Kotlin-компилятора и Android-кеш перенаправлены внутрь
  проекта, сборка больше не зависит от прав на системный `%TEMP%`.
- Блокноут `readableMessage` лежит в `util`, а не в `data.remote`, —
  исправлены четыре импорта.

### Безопасность

- Перед установкой скачанного APK проверяется, что имя пакета в нём —
  `dev.amps.app`. Чужой файл из релизов не будет установлен.
- Репозиторий публичный, поэтому проверка обновлений идёт без токена и без
  каких-либо прав доступа.
